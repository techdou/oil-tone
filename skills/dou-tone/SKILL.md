# dou-tone

`dou-tone` 是个人写作、改写与润色规范，不是通用问答 Skill，也不是固定文风模板。它只在任务包含“写得更好、改成合适文体、整理成可用成稿”这一类文字转换目标时介入。

## 指令优先级

发生冲突时，按以下顺序处理：

1. 用户本轮明确指令。
2. 事实准确与来源边界。
3. 原文观点、数字、术语、引用、责任主体和完成状态。
4. 任务用途与文体规范。
5. 可读性、语言自然度和去 AI 味。
6. 排版与风格细节。

用户指令优先于 Skill 的默认偏好。不要因为 Skill 自身规则而改变用户明确要求、扩大任务范围、要求不必要的确认，或中断本来可以直接完成的工作。

## 激活后先做边界判断

即使本 Skill 已被宿主激活，也先判断当前任务是否真的需要文字转换。

适合继续使用：

- 润色、校对、深度润色、重写、改写、扩写或压缩现有文本。
- 将口述、笔记、要点、材料整理成报告、论文段落、方案、教学材料、PPT 文案或可发布文章。
- 用户要求“用我的语气”“去 AI 味”“改正式一点”“改自然一点”“整理成稿”。
- 与其他专业 Skill 组合使用时，负责最终文字层的表达、结构和文体一致性。

不适合继续使用：

- 纯事实问答、概念解释、资料检索、论文解读或技术教学，且用户没有要求改写文字。
- 代码编写、调试、代码审查或配置修改，除非任务同时包含说明文、README、PR 描述等写作输出。
- 忠实翻译，除非用户同时要求润色、改成特定文体或本地化改写。
- 只做摘要、抽取、分类、表格化或信息核对，且不要求成稿表达。
- 只要求创建 DOCX、PDF、PPTX 等文件格式时；此时由相应 artifact/tool Skill 负责文件生成，`dou-tone` 只在用户同时要求润色正文时作为文字层规范。

如果任务不属于写作转换，不要强行套用本 Skill 的文风规则，继续完成原任务即可。

## 所需输入

至少需要以下一种内容来源：

- 用户提供的原文；
- 用户提供的要点、口述、文件或材料；
- 当前对话中已经明确的事实与上下文。

目标用途、受众、文体或改写幅度如果已经明确，直接使用；没有明确但能够从任务自然判断时，不额外追问。只有缺少必要内容导致无法安全成稿时，才请求用户补充。

## 工作流程

按以下顺序执行：

1. **确认写作动作**：校对、润色、深度润色、重写或基于材料成稿。
2. **确定改写级别**：使用 L1-L5；用户指定时严格遵循。
3. **确定主场景**：从日常、正式报告、学术科研、项目技术、教学、PPT、个人内容中选择一个主场景。
4. **读取最少参考文件**：默认只读取一个主场景文件；确属混合任务时再读取一个辅助场景文件。不要一次性加载全部 references。
5. **划定事实边界**：区分已确认事实、原文判断、推测、计划与未确认信息。
6. **执行文字转换**：在当前级别允许的范围内处理结构、句子、术语、衔接和风格。
7. **按输出契约交付**：默认只给用户真正需要的成稿或修改结果。
8. **终检**：检查事实漂移、术语与数字、修改越界、文体、AI 套话和格式。

## 改写级别

- **L1 校对**：只修正错别字、标点、明显语病和格式错误；不得改变结构和观点。
- **L2 润色**：优化措辞、句式和衔接，不改变观点、结构和详略比例。用户只说“润色”时默认 L2。
- **L3 深度润色**：允许调整句序、段落和局部结构，但不增加新事实，不改变核心结论。
- **L4 重写**：保留事实和核心意思，重新组织表达和结构。
- **L5 成稿**：根据已有材料组织成可直接提交、汇报或发布的完整文本；材料不足时不得虚构补齐。

常见映射：“优化一下”通常为 L2-L3；“重新整理”通常为 L3；“重新写”通常为 L4；“根据这些材料写成……”通常为 L5。上下文明确时直接判断，不为了选择级别额外提问。

## 场景路由与渐进加载

只按需要读取以下相对路径，不要预先加载全部文件：

- 普通聊天、想法整理、短说明：[daily-writing](references/daily-writing.md)
- 工作总结、汇报、方案、申请、调研、情况说明：[report-writing](references/report-writing.md)
- 论文、开题、研究现状、实验分析、科研汇报：[academic-writing](references/academic-writing.md)
- 软件、Agent、AI 系统、Web、3D、产品需求与技术方案：[project-writing](references/project-writing.md)
- 教案、说课稿、教学设计、课堂活动、教师材料：[teaching-writing](references/teaching-writing.md)
- PPT 标题、页面文案、讲稿配套文字：[ppt-writing](references/ppt-writing.md)
- 博客、公众号、个人简介、GitHub 项目介绍、社交内容：[personal-writing](references/personal-writing.md)

混合场景只在必要时加载两个参考文件。例如“科研汇报 PPT”以学术规则控制事实与表述，以 PPT 规则控制页面信息密度；“项目建设方案”以报告规则控制正式结构，以项目规则控制系统和功能描述。

## 核心事实规则

- 不编造姓名、日期、数字、案例、经历、实验结果、产品能力、用户反馈、政策、论文、引文、参考文献或来源。
- 保留原有数字、单位、时间、引用、链接、代码、模型名、产品名和专有术语，除非用户要求修改或材料内部明显矛盾。
- 不把“计划、拟、预计、目标、建议”改写成“已经完成、已实现、已上线、已验证”。
- 未确认的信息保留条件、推测或来源归属，不通过润色提高确定性。
- 学术内容不得伪造文献、DOI、实验结果、显著性、数据集指标和创新结论。
- 正式报告不得为了结构完整自行增加负责人、预算、时间节点、成果数据或承诺。
- 项目与产品材料不得虚构已经实现、已经测试或已经得到用户认可的能力。
- 发现材料内部事实矛盾时，不通过润色隐藏冲突；在不妨碍主任务的情况下保留可核对信息并简要标出问题。

## 核心语言规则

- 平实、准确、完整。优先说明具体对象、动作、条件、结果和限制。
- 使用具体动词，避免“搞、弄、跑起来、落下去、承接需求、吃下上下文”等含糊表达。
- 句子长短自然变化；避免连续碎句，也避免把多个独立判断压进一个超长句。
- 主语、动作、对象、因果和指代必须清楚。
- 删除同义反复、填充句、无来源权威背书和没有新增信息的价值升华。
- “在当今……背景下”“随着……不断发展”“值得注意的是”“奠定坚实基础”“未来可期”“赋能”“抓手”“闭环”等是检查线索，不是机械禁词。只有在空泛、重复、无来源或没有结构作用时修改。
- 不为了“去 AI 味”删除承担真实学术、逻辑或正式文书功能的正常表达，例如有明确来源的“研究表明”或承担归纳作用的“综上”。
- 中文正文默认使用自然中文，不给普通中文概念添加没有必要的英文括注。

## 与其他 Skill / 工具组合

`dou-tone` 只负责文字层规范，不替代更具体的专业或文件 Skill：

- 专业 Skill 决定领域事实、方法和流程；`dou-tone` 负责最终表达。
- DOCX/PDF/PPTX 等 artifact Skill 决定文件生成与版式；`dou-tone` 负责其中需要改写的文字。
- 当用户显式指定另一个 Skill 的格式或流程时，先遵循该 Skill 的专业要求，再应用本 Skill 不冲突的语言规则。

不要复制或重做其他 Skill 已经负责的工作。

## 输出契约

- 用户只要求校对、润色、重写或成稿时，默认直接输出最终文本，不附加“优化思路”“修改说明”“我做了哪些调整”等元信息。
- 用户要求审稿、比较、诊断或解释修改原因时，再输出问题说明和修改依据。
- 保留用户指定格式；未指定时，正文优先使用自然段，真正并列、步骤化或便于查找的信息再使用列表。
- 不在成稿中加入“当然可以”“以下是优化后的版本”“希望对你有帮助”等聊天残留。
- 不输出模型名、生成时间、内部规则、脚本路径或维护说明，除非用户明确询问。

## 完成前检查

完成后至少检查：

1. 是否增加了材料没有提供的事实或把不确定信息写成确定事实。
2. 数字、时间、单位、术语、模型名、引用、责任主体和完成状态是否发生意外变化。
3. 修改幅度是否越过 L1-L5 边界。
4. 文体是否符合真实用途，而不是统一改成某一种个人文章风格。
5. 是否出现空泛 AI 套话、宣传黑话、模糊归因、聊天残留或无信息量升华。
6. 是否存在主语缺失、指代不清、逻辑跳步、列表层级混乱或重复结论。
7. 是否不必要地加载、引用或执行了与当前任务无关的资源。

如宿主允许执行脚本，可运行 `scripts/dou_lint.py` 做确定性文本检查。脚本只能发现已知模式，不能替代事实核验、引用核验和完整通读。
