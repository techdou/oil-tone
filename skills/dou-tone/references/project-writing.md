# 项目与技术写作

适用于软件系统、AI Agent、Web 应用、3D 仿真、产品需求、技术方案、开发说明、接口说明和甲方需求整理。

## 表达模型

优先写清楚：谁使用 → 在什么场景 → 输入什么 → 系统如何处理 → 输出什么 → 有什么限制或依赖。

## 规则

- 用工程语言描述真实能力，不用营销口号替代功能定义。
- “支持、实现、完成、上线、自动、实时、智能”等词必须与实际能力一致。
- 功能需求描述到用户能理解验收标准的程度；用户没有要求实现细节时，不自行扩展技术栈和架构。
- 技术方案中区分需求、设计、实现、测试和部署，不混写成同一层级。
- 数据流和调用关系必须明确，避免“接一下、跑一下、处理一下、承接需求”等含糊动作。
- 涉及模型或第三方服务时，区分模型能力、系统封装能力和业务承诺。
- 未确认的性能、并发、延迟、成本、准确率和兼容性不得写成确定指标。
- 对甲方材料保持专业、清楚、中性，避免过度技术化，也避免“打造生态、全面赋能”等宣传语。

## 推荐结构

按任务选用：

- 项目背景 / 使用对象 / 使用场景 / 核心需求 / 功能流程 / 管理端 / 数据与权限 / 非功能要求 / 交付边界。
- 问题 / 现状 / 目标 / 方案 / 模块 / 流程 / 风险与限制。

短需求不强制套完整章节。

## Prompt 与 Agent 需求

如果用户要求“给另一个 Agent 的开发 Prompt”，重点描述身份、场景、目标用户、业务流程、功能边界、验收意图和设计约束。除非用户明确要求，不替目标 Agent 决定低层实现细节。
